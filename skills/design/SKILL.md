# デザインの統一入口

利用者が何を理解・判断・実行したいかから、構成と制作方法を選ぶ。必要なガイドは内部で読み、利用者へ別スキルの選択や再依頼を求めない。

## 1. 対象と完了条件

依頼、添付、既存成果物、README、適用指示から、利用者・場面・目的、事実の正本、ブランド、変更範囲、出力形式・編集性・共有先を確認する。既存媒体と技術を優先し、局所修正を全面移行へ広げない。自己調査で分かることは調べ、成果を左右する不明点だけ確認する。

現状（As-Is）、将来構想（Vision）、合意済みの目標状態（To-Be）、実装・検証済みの事実を区別する。構想の記録を、要求の採用・実装の承認・動作確認と同一視しない。詳細は[共通原則](references/principles.md)に従う。

創作を伴う新規制作では骨子・ラフ・本番の段階を示す。既に採用された構成や本番の依頼を再承認待ちにしない。調査・レビューだけなら編集や公開を行わない。

## 2. 原則と媒体

制作前と検証時に [共通原則](references/principles.md) を読む。WebとHTML資料では [Web UI基準](references/web-ui.md) も読む。ユーザーの明示指示、既存のデザインシステム、DADSの順に優先する。公式規定、パッケージの採用判断、案件の例外は [出典](references/sources.md) のように区別する。

| 目的 | 読むガイド |
| --- | --- |
| 画面・SPA・フォーム | [Web UI](references/web-ui.md) |
| 解説・提案・設計・進捗・HTMLプレゼン | [HTML資料](references/html-documents.md) |
| 骨子や説明のつながり | [読む資料の構成](references/document-story.md) |
| 構成図・フロー・比較・操作して学ぶ教材 | [図解・教材](references/diagrams.md) |

必要な主媒体と補助手順だけ組み合わせる。印刷物・静的図解へWebのCSS pxやフォーム規則をそのまま転用しない。専門的な数学・業務判断は別に正確さを検証する。見た目の制作から業務状態や数値を確定しない。

## 3. 制作、保存、公開

原稿・正規化データ、表示、保存、公開を別工程にし、正本を増やさない。資料やTODOの表示だけでDB・API・認証・共同編集を追加しない。保存を依頼された場合は既存保存先を確認し、成功前の保存済み表示を避け、失敗時の入力保持と再読込などを検証する。

閲覧用HTMLで公開までが承認済みの完了条件なら、利用環境の既存公開先とCI経路を使い、CI成功・対象commitと公開版の一致・公開画面の主要操作まで確認する。公開先または経路が未設定なら不足と必要な次の操作を報告する。このスキル自体は公開権限を与えない。明示された公開を再確認せず進めるが、任意の新しい公開先へ範囲を広げない。

ローカルのみ・オフライン納品、調査・レビュー・構成案だけの依頼では公開しない。PDF変換の中間HTML、メール本文、テストfixtureも閲覧用Web公開の対象ではない。secretや非公開原本を公開物へ含めない。メール・投稿・印刷や外部計測は、明示された範囲だけ行う。

## 4. 検証と引き渡し

[検証ガイド](references/verification.md) と選んだ媒体の基準を使う。見た目と目的達成を別に確かめ、未実装・未測定を成功扱いしない。成果物、検証結果、未確認事項を簡潔に示す。公開した場合はURL、公開日時、commit、CI実行へのリンクを含める。
