# 利用者中心の共通原則

利用者が必要な情報を見つけ、理解し、判断し、目的を達成できるようにする。[公式資料](sources.md)を参考にまとめた独自方針であり、政府の統合規格や適合宣言ではない。

制作前に、利用者の端末・言語・知識・時間的制約、達成したいこと、入口から完了までの流れ、根拠と不確実性、代表的な確認課題を整理する。既存の構成案へ統合し、票を増やさない。小さな改稿では変更部分だけでよい。

- 利用者が使う語でタイトル、見出し、分類、リンクを付ける。検索や途中流入、目次からも必要箇所へ到達できるようにする。
- 答え、対象条件、費用、制約、根拠を探せる順序で示す。専門語は説明し、平易さのために重要な条件を削らない。
- 入力・説明・選択肢の必要性を確かめ、再入力や不要な装飾を減らす。既存の使える部品を再利用する。
- 次の行動と完了状態を示す。確認・修正・エラー復帰、資料の前提や参照へ戻る道を用意する。
- 色だけに頼らず、読み順、代替表現、拡大、動き、翻訳後の長さを媒体に応じて確認する。
- 同じ意味に同じ用語・操作を使う。配置は内容の関係に合わせる。
- 好みだけで評価せず、誤解・迷い・負担・目的達成の証拠から改善する。数値や利用者の反応を捏造しない。

フォームは必要な質問だけを尋ねる。1ページ1質問は検討の出発点であり、全UIや資料の固定規則ではない。販売導線でも、購入を見送る判断を含め条件を理解して選べることを守る。根拠のない緊急性や条件の隠蔽を使わない。

国別の法制度、政府ブランド、二言語要件は参照元の条件と案件の要件を分ける。外観や演出が目的達成・アクセシビリティと両立しなければ、具体的な影響と代案を示す。

## 現状と構想の分離

設計・レビュー・説明資料では、確認できた現状と将来の可能性を同一の状態として描かない。構想を記録したことと、仕様・予算・公開・実装を承認したことは異なる。必要な区分は既存文書内で明示し、専用の表や文書をむやみに増やさない。

| 区分 | 記録の原則 |
| --- | --- |
| 現状（As-Is） | 現在の機能・データ・運用を、確認時点と証拠の範囲で記述する。未調査・推測は現状の事実にしない。 |
| 構想（Vision） | 将来の方向性や可能性を示す。採用範囲・責任主体・実現時期が未定なら、そのまま未決として扱う。 |
| 目標状態（To-Be） | 変更後に達成したい状態と、どこまで合意・採用されたかを記す。未承認なら「目標案」と示す。 |
| 設計案・決定 | 具体案と採否、主要な選択理由や制約を分ける。構想から実装案へ無断で飛躍しない。 |
| 実装・検証 | 実際に実装・配信・確認できた範囲だけを記録する。採用済みでも未実装、実装済みでも未検証の場合がある。 |

現状図と将来のフロー図、稼働中の画面とコンセプトモックは、見出し・凡例・状態ラベルなどで明確に区別する。未採用の機能を、現行操作・受入済みの機能として見せない。事実・課題・構想・提案・決定を追跡できるようにし、具体的な採用後に必要な要求・設計・受入条件を既存の正本へ反映する。

既存システムを改修するときは、現状の利用行動と確認できる問題から始める。構想は選択肢と判断の方向を与えるものであり、それだけで実装を命じるものではない。小規模な修正なら一文で状態を区別すれば十分とする。
